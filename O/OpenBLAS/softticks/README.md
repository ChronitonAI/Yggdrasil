# Software ticks for OpenBLAS's hand-written x86-64 kernels

On `x86_64-linux-gnu-rr_softticks` platforms every function and every loop must tick (rr's
tracee ABI, `include/rr/softticks.h`, version 1: no instrumented instruction may run twice in
one stack frame without a tick in between). The toolchain's compiler pass ticks what GCC and
gfortran compile, including LAPACK. OpenBLAS's x86-64 kernels are hand-written assembly
(`kernel/x86_64/*.S`) and C with inline-asm microkernels, which the compiler cannot see into.
They tick themselves with the patches in `OpenBLAS@0.3.34/bundled/patches`:

- `90-rr-softticks-macros.patch` (written by hand): `common_x86_64.h` defines `RR_SOFTTICK`
  (for `.S` files) and `RR_SOFTTICK_ASM` (a string for asm templates), the ABI's x86-64 tick
  byte for byte, ending at the local label `7731` instead of the ABI's `1` (a loop's own `1b`
  would otherwise jump to the tick's end and skip it). `PROLOGUE` ticks at the entry of every
  assembly function: interface and driver code call the kernels twice from one frame.
- `91-rr-softticks-kernels.patch` (generated by `regen.sh` with `asmticks.py`): a tick after
  every label that a later jump targets, in every `.S`, `.c` and `.h` file of `kernel/x86_64`.
  The kernels are laid out linearly, with no indirect jumps, `loop`/`jrcxz` or section
  switches inside functions, so every cycle passes through one of those labels.

Both macros are empty unless the compiler predefines `__RR_SOFTTICKS__` (the toolchain's
compiler plugin does, for `.S` files too), so the patches apply on every platform and change
nothing elsewhere: built without the macro, every object of a DYNAMIC_ARCH build is
byte-identical to one from the unpatched source. A `__RR_SOFTTICKS__` other than 1 is an error.

The tick clobbers the arithmetic flags. No tick in these kernels has a flag live after it:
the kernels set and test their loop counters at the bottom of the loop (`dec`/`sub`, then
`jnz`/`jg`) or before the loop's label, and none uses `adc`/`sbb` chains across a loop's
back edge, so nothing needs saving around a tick.

## The check

`check.pl` (Perl, which the build environment has) runs after `make shared`: it disassembles
every member of the archive the library is linked from and reports cycles without a tick,
assembled functions with a path from entry to exit without one, flags live after a tick,
countdown accesses outside a whole tick, and compiled objects without the ticks note; and it
checks that the library has the note and the initializer. The rewriter is textual; the check,
on the object code, is what catches a loop idiom it does not know (it caught cpp aliases of
jump mnemonics and labels pasted together from macro arguments). It needs an objdump that
decodes everything the kernels use (AMX, AVX-512): binutils 2.41 does, 2.35 does not
(`undecodable`).

## A new OpenBLAS version

Run `regen.sh VERSION` (and `regen.sh --check VERSION` to compare), build for
`x86_64-linux-gnu-rr_softticks`, and let the check judge the result. Hand-edit 90 if
`common_x86_64.h`'s `PROLOGUE` changes.

## Other architectures

Only x86-64 is done; the recipe refuses other `rr_softticks` targets. aarch64 would need its
own patches: the aarch64 tick clobbers x16 and x17 rather than the flags, and 41 of the 74
`kernel/arm64` `.S` files use those registers, so ticks there need x16/x17 saved around them
(or the kernels' registers renamed), and the inline-asm templates need `"x16", "x17"` added
to their clobber lists, which a string splice cannot do.
